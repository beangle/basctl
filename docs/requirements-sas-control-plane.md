# SAS 控制面与运行时拆分——开发需求文档

## 1. 文档目的

本文档汇总当前架构讨论结论，作为 **「sas」（D 语言控制面）** 与 **「sas-server」（运行时制品）** 拆分设计与实现的输入需求，供评审与排期使用。

## 2. 背景与问题

### 2.1 现状（beangle-sas）

- 产品定位为 **多实例 Tomcat 定制运行时**：一套安装目录下可管理多个 JVM/Tomcat 实例。
- 启停依赖脚本（如 `start.sh` / `stop.sh`），辅助工具入口为 `sas.sh`（版本、`proxy`、`firewall`、`status`、`pull`、`update` 等）。
- **代理配置**：`sas.sh proxy` 可生成 HAProxy/Nginx 配置，但默认提示将配置拷贝至 `/etc/haproxy/` 等 **root 路径**；若 HAProxy 在 **其它主机**，还存在 **配置分发** 不便。
- **多 JVM / 多端口**：远端 HAProxy 需要知晓「端口与上下文」的映射；实例增减时需同步改 HAProxy，手工维护易与真实拓扑漂移。
- **可选 systemd**：可作为生命周期管理补充；与「工具型中间件」心智不冲突。用户级 systemd（`systemctl --user`）可减轻对 root 的依赖。

### 2.2 待解决的核心矛盾

1. **拓扑与代理规则的双重维护**：期望 **单一数据源**，并能被远端 **拉取更新**。
2. **动态端口与防火墙**：动态端口若直接暴露给远端 HAProxy，易迫使 **防火墙/安全组频繁变更**；小规模场景希望 **固定对外端口**，动态后端留在本机。
3. **用户体验**：应用增多时，用户为每个实例 **手工挑选可用端口** 成本高，期望支持 **可选的动态端口分配**（由控制面负责），并与拓扑导出一致。

## 3. 产品愿景与打包形态

### 3.1 两个构件

| 构件 | 技术栈（规划） | 职责 |
|------|----------------|------|
| **sas** | D 语言 | **主交付物**：CLI、监控（健康/拓扑）、HTTP 反向代理（小规模场景）、编排入口；负责 **按需获取/更新 sas-server** |
| **sas-server** | JVM/Tomcat 侧（继承现有 beangle-sas 运行时能力） | **运行时本体**：Tomcat 应用运行所需制品（引擎、`bootstrap`、依赖库等），体积较大 |

### 3.2 打包与获取路径（硬性要求）

- **对外主打「sas」**：用户 **不必单独下载 sas-server** 即可完成日常流程。
- **sas-server 由 sas 自动下载**（或指向私有仓库/镜像），作为 **Tomcat 应用的运行时**；需定义 **版本兼容策略**（sas 与 sas-server 的版本区间或锁定关系）。
- **离线/内网**：必须支持 **缓存目录拷贝、私有源 URL、跳过在线校验** 等能力（具体命令与配置在详细设计中展开）。

### 3.3 命名与术语（避免歧义）

- **sas**：控制面二进制及相关配置（用户口中的「一条命令」）。
- **sas-server**：运行时压缩包/目录制品，非「某个业务 Tomcat 实例」的口语简称。
- **实例 / 节点**：仍指单个 JVM/Tomcat 进程及其 `catalina.base` 目录（与现有 `servers/<name>` 模型对齐）。

文档中需在用户手册 **显眼处** 区分「sas 守护进程」与「Tomcat 实例」，避免与历史「server」用语混淆。

## 4. 功能需求

### 4.1 sas——CLI

- 逐步承接现有 `sas.sh` 能力，路径可为：
  - **优先迁入 sas**：`status`、拓扑查询、代理片段导出、健康检查、与守护进程协作的启停指令等。
  - **可委托现有 JVM 工具**：`pull`、`update`、`aes`、`Maker` 等可通过 **子进程调用现有 JAR** 实现，避免短期内重写全部逻辑。
- 兼容策略：`sas.sh` 可 **瘦封装为调用 `sas`**，保证旧脚本路径过渡期可用。

### 4.2 sas——监控

- 暴露 **进程存活** 与 **实例拓扑**（实例标识、监听地址、端口、上下文路径、可选 Host、健康状态摘要）。
- 支持 **机器可读格式**（如 JSON），供自动化与其它系统消费。
- （可选）与动态端口、注册表一致：**实例上线/下线/端口变更** 后拓扑即时可查。

### 4.3 sas——HTTP 反向代理（小规模）

- **范围**：首期 **HTTP/1.1**（WebSocket 等可作为后续迭代明确列出）。
- **部署模型**：与监控 **同一进程**（低资源、运维简单）；监听 **固定对外端口**，后端指向 **本机动态端口**（如 `127.0.0.1:<dynamic>`），从而 **不因动态端口暴露而修改边界防火墙**。
- **路由数据**：与监控共用 **同一份内存路由表**（或等价单一数据源），更新策略需在详细设计中定义（文件监视、API 注册、子进程回调等）。

### 4.4 拓扑与 HAProxy/Nginx 集成

- **导出能力**：提供 **可下载** 的配置片段或清单（与现有 Freemarker 模板思路对齐时可复用 **生成规则**，避免两套 HAProxy 语义）。
- **远端 HAProxy**：支持 **HTTP(S) 拉取** 更新；建议支持 **校验（如 `haproxy -c`）后再 reload** 的流程说明或示例脚本（可由运维落地）。
- **用户指定固定端口时**：行为与现有一致——远端仍可 **拉配置** 做负载均衡，**直连各实例端口**；防火墙策略稳定。
- **推荐运维形态**：全局 HAProxy 使用 **`include` 片段**，避免整文件覆盖 `/etc/haproxy/haproxy.cfg`；生成物可先落到 **staging**，再通过 **受限特权步骤** 安装与 reload（文档化即可，不要求 sas 必须以 root 写 `/etc`）。

### 4.5 动态端口（可选能力）

- **默认**：允许用户在配置中 **显式指定端口**。
- **可选**：控制面在约定范围内（如可配置 `PORT_MIN`/`PORT_MAX`，默认例如 9000 起）为实例 **分配空闲端口**，再写入实例生效配置并启动 JVM。
- **并发**：分配逻辑须 **避免双实例抢占同一端口**（串行化或 OS 级原子占用策略）。
- **与防火墙的关系**：动态端口 **默认仅本机或内网可达**；对外统一走 sas 反代固定端口或用户自建 HAProxy + 固定 upstream。

### 4.6 sas-server——运行时

- 承担现有 beangle-sas **运行时职责**：可被 sas **解压/校验/更新** 到约定目录（如缓存目录或 `SAS_HOME` 下层结构）。
- 与 sas 的 **版本契约** 需在发布清单中明确（changelog、兼容性矩阵）。

## 5. 非功能需求

- **资源**：sas 进程目标为 **低开销**（相对 JVM 常驻监控方案）。
- **安全**：导出与反代接口默认 **内网或 TLS + 令牌**；禁止未鉴权的远程执行任意命令。
- **可靠性**：sas 崩溃时的恢复策略（systemd `Restart=`、supervisor 或文档化手工重启）；反代与监控同进程带来的 **故障域** 需在文档中说明。
- **可观测性**：结构化日志、可选 metrics（后置）。

## 6. 仓库与工程边界（建议）

- **sas**：独立仓库（或后续纳入 monorepo 子目录），**dub** 工程，独立 CI。
- **sas-server**：现有 beangle-sas 构建产物演进；发布流水线产出 **可被 sas 消费的压缩包/清单**。
- 本文档存放于 beangle-sas 仓库仅作 **跨项目需求对齐**；sas 仓库成立后可将本文档 **迁移或同步**。

## 7. 里程碑建议（供排期）

1. **M1**：sas CLI 骨架 + 调用现有 JVM 工具链（`status`/代理生成委托路径清晰）。
2. **M2**：常驻模式 + JSON 拓扑 API + 固定端口反代最小闭环。
3. **M3**：远端拉取导出片段 + 文档化 HAProxy `include` / staging / reload。
4. **M4**：动态端口分配 + 与拓扑/导出一致。
5. **M5**：sas 驱动 sas-server 下载、校验与版本策略 + 离线安装说明。

## 8. 开放问题（详细设计阶段闭环）

- sas 与 Tomcat 实例之间的 **注册协议**（文件、Unix socket、HTTP 回调）。
- 是否与现有 `Maker`/`server.xml` **生成流程** 合并为单一触发链。
- TLS 终止位置（sas 反代 vs 外层 HAProxy）及证书 rotation。
- 多机 sas 拓扑（是否只做单机控制面）。
